Identidad visual & sistema de theming white-label

Al elegir un balneario, la app deja de ser EasyBeach y se convierte en la app del balneario: paleta íntegra, logo, tipografía de un set curado, imágenes y splash. Este documento define la identidad de plataforma (ámbito acotado), el contrato cerrado de tokens, la estrategia de accesibilidad bajo sol directo y el design system base — validado con tres balnearios ficticios de personalidades opuestas.

01

Identidad de plataforma EasyBeach

Ámbito acotado por diseño: esta identidad vive únicamente en el onboarding, el selector de balneario y los paneles web de staff. Dentro de una estadía, la marca EasyBeach no existe para el cliente. La paleta y las tipografías se derivan directamente del logo provisto.

02

Sistema de theming white-label

Principio rector: el balneario es dueño de la estética; la plataforma es dueña de la estructura. Todo lo que se ve tiene token; todo lo que no tiene token es visualmente neutro. EasyBeach mismo es “un balneario más” para el motor de theming: los defaults del contrato son su propio theme, usado solo antes de la selección.

2a · Personaliza el balneario — capa visual completa

  • Paleta íntegra — primario, secundario, fondo, superficies y colores de estado. No hay “color EasyBeach” residual en la estadía.
  • Tipografía — una pareja (display + texto) elegida del set curado embebido en la app. No se suben fuentes arbitrarias: garantiza licencia y legibilidad al sol.
  • Assets de marca — logo, logo compacto, imagen de portada, splash de entrada, placeholder de producto.
  • Fotografía — fotos de productos y de portada cargadas por el admin del balneario.

Queda común — estructura visualmente neutra

  • Arquitectura de navegación — tabs, jerarquía de pantallas, flujos de estadía, carrito y pago.
  • Anatomía de componentes — layout de cards, steppers, inputs, trackers de pedido; solo cambian sus colores/tipos vía token.
  • Escalas fijas — espaciado, radios, sombras, tamaños tipográficos e iconografía funcional (lineal, geométrica, sin rasgos de marca).
  • Regla de neutralidad: si un elemento no es tematizable por token, debe ser gris/estructural. Nada naranja-y-azul “de fábrica” puede filtrarse a la estadía.

Fuera del contrato (comunes, no personalizables): escala de espaciado, radios, sombras, tamaños tipográficos, iconografía funcional, duración de animaciones y layout de componentes. Se definen en 03 y viven en el binario de la app, no en la API.

2c · Estrategia de accesibilidad — AA garantizado, elija lo que elija el balneario

1 Los pares “on-*” nunca se eligen: se derivan

El balneario elige 5 colores base + 4 de estado. La plataforma calcula cada on-* (blanco o tinta oscura, el que dé mayor contraste) y los derivados (muted, border, surface-variant) por desplazamiento de luminosidad en OKLCH manteniendo el matiz. Es imposible configurar texto ilegible.

2 Validación al configurar, con tono ajustado

El configurador (etapa 10, con preview en vivo) valida cada par en uso: ≥ 4.5:1 texto normal, ≥ 3:1 texto grande y componentes UI. Si un color falla, la plataforma propone el tono más cercano que cumple (ajuste de luminosidad, mismo matiz) y el guardado exige aceptarlo o corregir. La API nunca sirve un theme inválido.

3 Margen extra para sol directo

AA es el piso legal; la playa pide más. Precios, CTA de pedido y estados de pedido apuntan a ≥ 7:1 (AAA) — el configurador lo marca como “recomendado playa”. Refuerzos no cromáticos comunes: peso ≥ 600 en precios, ícono + texto en estados (nunca solo color), tamaños mínimos de 03.

Design system base — estructura neutra

Los componentes se documentan acá en gris estructural, sin theme: así se audita que la capa común no tiene rasgos de marca. Diseño para sol directo y mano mojada: targets ≥ 52 px en acciones primarias (48 px mínimo absoluto), cuerpo 17 px, precios en peso 700, estados siempre ícono + texto, sin gestos de precisión (nada de swipe fino ni long-press obligatorio).

05

Criterios de aceptación — verificación

✓
Lista de tokens cerrada e implementable 26 tokens con nombre / tipo / default / regla de personalización + campo theme.contract versionado (2b). Todo lo tematizable pasa por un token; agregar uno = subir versión.
✓
Mismo screen, 3 themes, contraste correcto Los 6 mockups de 04 comparten estructura pixel a pixel y flexionan de crema-luminoso a negro-dorado. Pares texto/fondo verificados ≥ 4.5:1 (teal 4.6, oro/negro 8.9, cobalto 8.3).
✓
Test white-label En los mockups de estadía no hay logo, wordmark, naranja #C95100, azul #17437B, Bricolage ni tono de voz EasyBeach. La regla de neutralidad (2a) + defaults = theme EasyBeach hacen el filtrado estructural: no existe valor visual “de fábrica” que sobreviva al theme.
✓
Cobertura de los user journeys del MVP Journey (a) doc 01: selector → transición (2d) → apertura de estadía (inputs, estado pendiente/activa) → menú con variantes y promos (card + stepper + badge) → carrito/CTA → seguimiento (6 estados de pedido) → servicios al carpero (botón secundario) → cierre de estadía. Empty states para pedidos e historial. Todo en 03–04.
